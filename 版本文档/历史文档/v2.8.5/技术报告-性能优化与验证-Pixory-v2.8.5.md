# Pixory 性能优化与验证报告

## 1. 目标与结论口径

本文记录当前源码已经采用的性能策略，并把尚未完成的真实设备验证单独列出。性能优化优先服务于陪伴聊天连续性、长线程可读性、原始素材安全和低内存设备稳定性。

## 2. 主要性能瓶颈

| 场景 | 风险 |
|---|---|
| 长线程流式回答 | patch 过密、布局抖动、JS/UI 掉帧 |
| 图片/视频大量浏览 | 列表增长、解码峰值、播放器过多 |
| 记忆与材料检索 | 查询超时拖慢首字节 |
| SQLite 迁移和导入 | 锁等待、磁盘峰值、半完成记录 |
| Personal 切换 | 缓存和后台任务越权、关闭不及时 |
| 诊断采集 | 指标过多导致额外 IO 和隐私风险 |

## 3. 已实现的优化策略

### 3.1 流式 UI

- 依据底部锁定、尾部热区和内容长度动态调节目标帧率。
- 底部锁定且文本不长时目标约 60 FPS；内容变长或压力升高时降至 45/30 FPS。
- 用户脱离底部时约 12 FPS，避免后台滚动和不可见更新争用主线程。
- patch 合并依据 backlog、文本长度和压力提高显示步长。
- 普通压力每约 500ms 持久化，高压力每约 1000ms；后台、路由离开、停止、完成、错误强制 flush。

### 3.2 尾部视口与布局

流式尾部按 cold、warming、active 三个热区管理。active 区放宽裁剪窗口并预热下一个完整块；块高采用单调保留高度，缩小欠账延后偿还，避免文字测量变化导致滚动跳动。

### 3.3 列表与媒体

- 图片使用有界 FlatList 和 keyset 游标，单页约 48 项。
- 视频使用锚点 + 游标，当前及前后窗口保留，最多准备 3 个播放器。
- Personal 图片缓存只在内存存在。
- 查询索引覆盖 IP、删除状态、创建/访问时间和主键。

### 3.4 检索

- 关键词检索先行；向量缓存有 5 分钟 TTL 和数量上限。
- 查询向量超时约 250ms 退回关键词模式。
- 记忆最多注入 6 条，材料检索默认限制 6 条。
- 每次检索记录 mode、partial、timedOut，便于识别“慢但未失败”。

### 3.5 生成持久化

本地先写用户消息和占位消息，再发请求。生成管理器以 space:thread 互斥，避免两个任务同时写同一线程。恢复租约约 2 分钟，迟到事件用 generationId 过滤。

### 3.6 数据库和文件

SQLite 开启 WAL、外键和面向常用列表的复合索引。导入使用最多 4 个 worker，并做数量、大小、批次容量和剩余空间门槛预检。临时文件清理服务按 48 小时最大年龄和每日周期运行。

## 4. 预算和降级

默认模型窗口 512,000 token，安全预算为窗口的 70%，生成预留至少 512 token 或安全预算的 12%。裁剪顺序为动态→受保护→稳定，必需的当前问题和摘要桥不删除。

检索压力高时关闭图扩展和验证器，记忆最多保留 3 条；向量服务不稳定时使用关键词模式。所有降级写入诊断和生成指标。

## 5. 指标定义

| 指标 | 含义 |
|---|---|

| provider.firstByteMs | 请求发出到提供商首字节 |
| chat.firstUiPatchMs | 首个流式 patch 可见时间 |
| render.jsFrameP95 / uiFrameP95 | JS/UI 帧耗时 p95 |
| chat.blankScreenDurationMs | 空白屏嫌疑持续时间 |

## 7. 性能验收建议

1. 记录低、中、高端 Android 设备的首字节、首个 UI 可见、首个 UI patch、完成时间、JS/UI p95、峰值内存。
2. 长线程至少覆盖 100、500、1000 轮，并分别测试有/无材料、有/无记忆。
3. 流式测试底部锁定、用户上滑、切后台、路由离开和停止五种状态。
4. 导入测试小文件、超大图片、混合媒体、重复文件和空间不足。
5. 对比优化开关前后，若性能变差不得仅以平均值掩盖 p95 和掉帧。

## 8. 剩余风险

- 真机设备矩阵和长时间后台任务仍需补齐。
- 真实备份恢复耗时、空间峰值和失败回滚需要记录。
- 服务端缓存尚未实现，当前性能结论只覆盖本地和客户端提供商链路。

## 9. 性能模型与预算

### 9.1 聊天首屏时间分解

聊天首个可见 UI 时间可拆为：

~~~text
T_first_ui =
  T_route
  + T_local_read
  + T_history_merge
  + T_memory_plan
  + T_retrieval
  + T_prompt_build
  + T_provider_first_byte
  + T_ui_commit
~~~

其中 T_memory_plan 和 T_retrieval 可以并行准备，但不能以 Promise.all 无界并发方式实现；二者必须共享当前 generation 的取消信号、空间和版本上下文。指标系统分别记录每段耗时，避免只看总耗时无法定位瓶颈。

### 9.2 长列表内存模型

列表峰值内存近似为：

~~~text
M_peak =
  M_visibleRows
  + M_mountedWindow
  + M_encodedCache
  + M_decodedCache
  + M_prefetchTasks
  + M_nativePlayer
~~~

因此图片使用有界 FlatList、编码/解码分层缓存和速度自适应预取；视频使用有限播放器池和单音频 owner。Personal 额外要求退出/锁定时释放内存缓存。

## 10. 各优化方案的替代方案比较

| 问题 | 当前方案 | 可选方案 | 未采用原因 |
|---|---|---|---|
| 聊天历史分页 | keyset + 锚点 | offset 分页 | 大数据集翻页会因插入导致跳页 |
| 流式渲染 | patch 合并 + FPS 降级 | 每个 delta 立即 setState | 高频布局、掉帧和电量开销 |
| 图片预取 | 速度/方向/内存自适应 | 固定三页 | 快速滑动时浪费或不够 |
| 视频播放 | 5 槽池 | 每项独立播放器 | 解码和音频资源不可控 |
| 诊断写入 | 窗口聚合后批写 | 每事件立即写库 | 与聊天事务竞争并造成锁等待 |
| 大批量导入 | 4 worker + commit budget | 无界并发 | 磁盘抖动、内存峰值和难回滚 |

## 11. 性能故障复现方法

### 11.1 流式卡顿

固定同一线程、模型和消息，分别测试 1000、4000、8000 字符输出；记录 bottomLocked、detached、backlog、targetFps、UI patch 数、JS/UI frame p95、persist delay。若只在 detached 状态卡顿，优先看隐藏尾部是否仍在布局；若 bottomLocked 也卡顿，检查 patch 合并和文本测量。

### 11.2 列表白屏

固定数据量和筛选条件，记录 visibleItemCount、mountedItemCount、contentHeight、layoutCount、viewport、scrollOffset、threadMatch 和最近一次 UI commit。满足“有数据但可见/挂载为零”时生成 blank-screen suspicion，不直接把它当成渲染崩溃。

### 11.3 导入变慢

记录选择耗时、metadata 耗时、复制字节、hash 耗时、缩略图耗时、SQLite commit、失败数和 worker 数。若复制阶段慢，查看存储介质；若 commit 慢，查看锁等待和是否在同一连接并发事务。

## 12. 基准测试设计

### 聊天数据库

- 固定 6000 条消息、100 页；
- 测试 around-anchor、标题搜索、最后消息搜索、分支过滤；
- 比较单 statement 与多次查询的 p50/p95；
- 检查 query plan 使用复合索引。

### 媒体数据库

- 固定 100,000 行媒体；
- 测试 IP、标签、收藏、回收站和最近查看；
- 比较 offset 与 keyset 的 p95；
- 测试 normal/personal epoch 缓存命中和结构写失效。

### 视觉阅读器

- 图片 200/1000 项快速 fling；
- 视频 50 项连续上下滑；
- 低内存 trim、横竖屏、返回再进；
- 记录 RSS、帧耗时、预取命中、取消任务和播放器池占用。

## 13. 性能回归门槛

1. 任何优化不能让 P0 数据安全或恢复正确性下降。
2. p95 优先于平均值；必须同时报告冷启动、热启动和长时间运行。
3. UI 动效优化需在真实 Android 设备上检查掉帧和输入响应。
4. 只在模拟器或开发机验证的结论必须标记为“未完成真机验收”。
5. 优化失败时保留原有稳定路径，并能通过版本开关或回滚提交恢复。

## 14. 性能策略依据

### 14.1 动态帧率

流式文本、图片解码、数据库操作和系统动画共享有限的 CPU、内存与 UI 线程资源。固定追求 60 FPS 会在长文本、较大渲染 backlog 或低端设备上增加布局压力，反而推迟可见内容。当前策略优先保证输入响应、文本可读性和最终内容完整性，并在压力下主动降低不可见或非关键更新频率。

### 14.2 分位数指标

平均耗时容易掩盖低端设备、长线程和偶发数据库锁等待。性能评估以 p50 描述常见体验，以 p95 描述尾部体验，同时保留样本量、设备、线程长度和场景维度，避免用单一平均值判断优化是否有效。
