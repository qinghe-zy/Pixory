# Pixory 压缩包导入与按 IP 导出方案

更新时间：2026-05-05

## 目的

这份文档记录 Pixory 后续支持“压缩包导入图片资源”的可行方案，并明确导入、保存、导出边界。

核心目标：

- 支持从压缩包批量导入原图
- 导入后原图必须保存到 Pixory app 私有目录
- 导入结果不能混入系统相册或公开图片文件夹
- 压缩包内有文件夹时，文件夹名可映射为 Pixory 分组
- 压缩包内图片可能没有扩展名，需要尽量通过文件头识别真实图片格式
- 导出保持按 IP 导出即可；若未来已有按分组导出能力，可以保留，但不是第一优先级

## 当前项目基础

当前 Pixory 已经具备适合扩展该能力的基础：

- 原图保存目录：`documentDirectory/pixory/originals/ip_{ipId}/`
- 缩略图保存目录：`documentDirectory/pixory/thumbnails/ip_{ipId}/`
- 临时目录：`documentDirectory/pixory/temp/`
- 数据库存储：SQLite
- 当前导入链路：从系统相册选择图片后，复制原图到 app 私有目录，再生成单独缩略图并写入数据库
- 当前导出链路：支持全量备份和按 IP 备份，备份内按 `originals/ip_{ipId}/` 与 `thumbnails/ip_{ipId}/` 保存文件

需要注意：

- app 私有目录中的图片通常不会被 Android 系统相册扫描到
- 用户主动选择系统目录执行“导出数据”后，导出的真实图片文件可能被系统相册扫描
- 因此“导入保存不公开”和“导出到公开文件夹可能被扫描”是两个不同场景

## 推荐产品定义

建议把该能力命名为：

```text
资源包导入
```

不建议第一版叫“安装包导入”，避免用户误解为 Android APK 安装包解析。

推荐支持的文件类型：

- `.zip`
- `.pixorypack`

其中 `.pixorypack` 可以本质上仍是 zip，只是作为 Pixory 专用资源包后缀，便于后续迁移和备份闭环。

## 压缩包导入流程

标准流程：

```text
选择 zip / pixorypack
→ 复制压缩包到 Pixory 私有 cache 或 temp
→ 解压到 Pixory 私有 temp 子目录
→ 扫描解压目录
→ 识别图片文件
→ 根据文件夹路径创建或匹配 Pixory 分组
→ 复制原图到 originals/ip_{ipId}/
→ 生成单独缩略图到 thumbnails/ip_{ipId}/
→ 写入 SQLite 图片、分组、标签等记录
→ 清理 temp
→ 显示导入结果
```

导入过程中禁止：

- 把原图保存到 `DCIM`、`Pictures`、`Download` 等公开目录
- 调用系统相册保存 API
- 压缩、裁剪、重编码或覆盖原图
- 使用缩略图替代原图
- 长期依赖压缩包解压后的临时路径

## 文件夹到分组的映射规则

压缩包结构示例：

```text
角色A资源包.zip
├─ 春节/
│  ├─ 001.png
│  └─ 002.jpg
├─ 海报/
│  └─ kv-main
├─ 表情/
│  └─ smile.webp
└─ manifest.json
```

导入后的 Pixory 结构：

```text
IP：角色A
├─ 分组：春节
├─ 分组：海报
└─ 分组：表情
```

物理文件仍保存为：

```text
pixory/originals/ip_{ipId}/
pixory/thumbnails/ip_{ipId}/
```

分组关系写入 SQLite，而不是依赖物理文件夹。

这样做的原因：

- 后续修改分组不需要移动原图
- 可以兼容一张图片属于多个分组的现有模型
- 原图路径更稳定
- 导入失败时更容易回滚

建议第一版规则：

- 一级文件夹名映射为分组名
- 多级文件夹可以先取最近一级文件夹作为分组名
- 根目录图片导入为“未分组”或直接导入当前 IP，具体由 UI 文案确认
- 同名分组复用已有分组，不重复创建
- 文件夹名为空、非法或过长时，使用安全截断后的名称

## 无扩展名图片识别

用户压缩包里的图片可能没有扩展名，例如：

```text
春节/001
海报/kv-main
```

第一版应支持“无扩展名但有标准图片文件头”的情况。

识别优先级：

1. 读取文件头 magic bytes
2. 如果文件头无法识别，再参考扩展名
3. 两者都无法识别则跳过，并在导入结果中显示失败原因

建议支持：

- PNG
- JPEG
- WebP
- GIF
- BMP
- HEIC / HEIF，视当前运行环境和缩略图能力确认

不建议支持：

- 无容器格式的裸 RGB / RAW 二进制
- 无法识别尺寸、编码方式或 MIME 类型的未知文件

保存策略：

- 原图内容原样复制，不压缩、不重编码
- 如果原文件无扩展名，内部文件名可以补上识别出的安全扩展名
- `originalFilename` 保留用户包内原始文件名
- `internalFilename` 使用 Pixory 生成的安全文件名
- `mimeType` 使用识别出的真实 MIME 类型

示例：

```text
压缩包内：春节/001
识别结果：image/png
私有保存：pixory/originals/ip_1/001_20260505153000_ab12cd.png
数据库 originalFilename：001
数据库 mimeType：image/png
```

## 安全与可靠性要求

压缩包导入必须重点处理：

- Zip Slip 路径穿越，例如 `../../evil.png`
- 解压后总体积过大
- 文件数量过多
- 单文件过大
- 嵌套目录过深
- 空间不足
- 解压中断
- 图片识别失败
- 缩略图生成失败
- 数据库写入失败
- 导入部分成功后的清理和回滚

建议第一版设置保守限制：

- 单次导入最大文件数
- 单个压缩包最大体积
- 解压后最大总体积
- 最大目录深度
- 支持的图片 MIME 白名单

失败处理建议：

- 单张失败不阻塞整包导入
- 已经成功导入的图片保留
- 失败条目进入导入结果页
- 如果某张图数据库写入失败，应删除已复制原图和缩略图
- 导入结束后清理本次 temp 目录

## 导出策略

当前需求中，导出按 IP 即可。

当前项目已有按 IP 备份结构，方向可保留：

```text
exports/backups/ip_1_时间戳/
├─ database/
│  └─ pixory.sqlite
├─ originals/
│  └─ ip_1/
│     └─ 原图文件
├─ thumbnails/
│  └─ ip_1/
│     └─ 缩略图文件
└─ manifest.json
```

如果未来已有按分组导出能力，可以保留，但不是压缩包导入的前置需求。

需要明确提示：

- 导出到系统公开文件夹后，图片可能被系统相册扫描
- 这是 Android 公开存储行为，不代表 Pixory 私有库泄露
- 如果用户希望导出后也不混入系统相册，推荐后续新增“导出为单个 Pixory 资源包”模式

推荐后续可选导出模式：

```text
导出为 Pixory 资源包
→ 生成单个 .pixorypack
→ 内部包含 manifest、原图、缩略图、数据库或必要元数据
→ 系统相册不会扫描压缩包内部图片
```

## 第一版建议范围

建议第一版只做：

- 从文件选择器选择 `.zip` / `.pixorypack`
- 解压到 Pixory 私有 temp
- 扫描图片
- 支持无扩展名图片的文件头识别
- 文件夹名映射到 Pixory 分组
- 原图复制到私有 originals
- 缩略图单独生成
- 写入 SQLite
- 显示成功数、失败数、跳过原因
- 清理 temp

暂不做：

- APK 解析
- 云端导入
- 在线资源下载
- 复杂 manifest 规则
- 标签分类体系
- 图片内容去重
- 按分组物理移动原图
- 公开文件夹自动隐藏的强保证

## 验收标准

功能验收：

- 选择压缩包后可以导入多张图片
- 压缩包内一级文件夹能转换为 Pixory 分组
- 无扩展名 PNG/JPEG/WebP 能识别并导入
- 未识别文件会跳过并显示原因
- 导入完成后图片在目标 IP 中可见
- 图片详情中原图文件存在，缩略图文件存在，数据库记录存在

安全验收：

- 导入结果不出现在系统相册
- 原图保存路径位于 Pixory app 私有目录
- 不调用系统相册保存 API
- 临时解压目录导入后被清理
- 路径穿越文件不会写出 temp 目录
- 导入失败不会留下孤立数据库记录或孤立文件

导出验收：

- 按 IP 导出仍可生成独立备份目录
- 导出目录中只包含该 IP 的图片和必要元数据
- 导出到公开文件夹时，UI 应提示图片可能被系统相册扫描

## 结论

该能力可行，并且符合 Pixory 的产品方向。

推荐落地原则：

```text
导入必须私有、安全、按文件夹建分组。
导出按 IP 保持清晰；需要避免相册混入时，优先导出为单个资源包。
```
