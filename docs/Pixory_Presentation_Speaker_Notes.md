## 附录：HTML 演示大屏一键导出 PPT / PDF 保姆级指南

当你拿到生成的 `docs/pixory-presentation.html` 后，可通过以下三种方式转为 PPT 供你自由编辑插图：

### 方案 A：通过浏览器打印无损转为 PPT（推荐，排版 100% 像素级对齐）
1. 在 Chrome 或 Edge 浏览器中双击打开 `docs/pixory-presentation.html`；
2. 按快捷键 `Ctrl + P`（Mac 上为 `Cmd + P`）呼出打印窗口；
3. **关键参数设置**：
   * **目标打印机**：另存为 PDF（Save as PDF）；
   * **布局**：横向（Landscape）；
   * **纸张尺寸**：选择 `16:9` 或默认 `A4`（代码已内嵌 `@media print` 强制 16:9 分页，无任何跨页截断）；
   * **边距**：无（None）；
   * **选项**：勾选“背景图形”（Background graphics）；
4. 点击“保存”，导出为 `Pixory_Deck.pdf`；
5. 打开 PowerPoint（Office 365 或 WPS），点击菜单栏 **“插入” $\rightarrow$ “对象” $\rightarrow$ “由文件创建”**（或直接在 WPS 中使用 **“PDF 转 PPT”** 官方免费功能），瞬间即可转换为每一页都可以插入真机截图的 PPT 文件！

### 方案 B：直接在浏览器中全屏放映（科技感最强，无需安装 Office）
1. 浏览器打开 `docs/pixory-presentation.html`；
2. 键盘轻按字母键 `F`，页面自动切换至 **1920×1080 沉浸式极客大屏全屏放映模式**；
3. 使用键盘 `←`（左箭头）和 `→`（右箭头）或空格键自由切页；
4. 屏幕共享时，直接选择该浏览器标签页共享，画面稳定、文字超高清矢量渲染。

### 4. 深度防追问底稿
*   **极限追问 1.1**：“为什么状态层选 Zustand 而不用成熟的 Redux 或 React Context？”
    *   **最优回答**：“React Context 在面对高频流式打字（每秒 30~50 字）时，会导致消费该 Context 的所有子组件发生大面积无效重绘；Redux 样板代码过重且包体积大。Zustand 是基于闭包的小型轻量状态机，支持细粒度的 Selector 选择性订阅，并且允许在 React 渲染树外直接同步触发状态更新（`getState()`），非常契合移动端大模型流式打字与后台恢复的高性能诉求。”
*   **极限追问 1.2**：“双模架构在代码层面是怎么解耦的？它们会互相污染吗？”
    *   **最优回答**：“代码物理级强解耦。伴聊代码集中在 `src/im/`，长聊代码集中在 `src/ai/`，两者依赖关系为 0，伴聊主屏入口代码行数严格控制在 150 行以内。两者仅通过底层的 SQLite 数据仓库与统一的生成调度器共享底层基础设施，确保各自业务快速迭代互不影响。”

## Slide 2: 本地素材与 IP 资产管理系统（File & Asset Management）

### 1. 页面视觉排版与插槽设计
*   **顶部标题区**：`LOCAL ASSET & PRIVACY SANDBOX` | 本地素材流水线与 Personal 物理沙盒
*   **主体左侧（无损资产吞吐与处理流程）**：
    *   **导入门禁（Preflight Gate）**：`MediaImportCommitBudget` 统一校验，限制 1000 实体 / 256MB 单文件 / 32GB 总盘余量。
    *   **有界并发流水线**：4-Worker 物理上限，Metadata 文件 I/O 前预检，绝不阻塞 UI 渲染主线程。
    *   **原件安全铁律**：原始照片/视频完整拷贝至应用私有目录，**永不压缩、永不裁剪、永不覆写**；独立生成 320px 缩略图用于列表浏览。
    *   **微秒级全文索引**：基于 SQLite FTS5 对素材分组、标签、备注建立倒排索引，250ms 防抖极速全局检索。
    *   **生命周期治理**：软删除移入回收站 $\rightarrow$ 物理清空二次确认 $\rightarrow$ Manifest V2 完整加密备份与无损迁移。
*   **主体右侧（Personal 私密空间物理双沙盒）**：
    *   **双数据库实例对比**：普通空间挂载 `pixory.sqlite`，私密空间挂载独立的 `pixory_personal.sqlite`（非普通打 `is_private` 标签）。
    *   **四步优雅锁闭机制（Graceful Teardown）**：
        1. 全局 Task Cancellation Token 立即失效，中断未完成推理；
        2. 等待正在进行的 SQLite 事务到达 `WAL Checkpoint`（防坏库）；
        3. 彻底释放并清空内存中的私密媒体 LRU 缓存；
        4. 物理关闭 `pixory_personal.sqlite` 数据库连接句柄。
*   **截图插槽**：
    *   `【插槽 2-A】`：IP 主题资产库网格与批量管理整理面板截图（宽:高 = 16:9）。

### 2. 核心展示指标与参数
*   **吞吐性能**：1000 张图文批量导入，内存峰值稳定在安全水位。
*   **文件安全**：原文件修改覆盖率为 0%，备份支持 ZIP / `.pixorypack`。
*   **检索响应**：本地素材全文搜索防抖 250ms，单分类限制 20 条，微秒级召回。

### 3. 现场 60 秒最优演讲词
> “第二页是 Pixory 的基石 —— 本地素材与 IP 资产管理系统。
>
> 伴随式 AI 的核心基础是‘材料’，用户往往有大量角色设定图、世界观参考文档和背景视频。
>
> 在工程设计上，我确立了三大铁律：
> 第一，**原件绝对安全**。导入的图片视频一律拷贝进私有目录，永不压缩、永不覆写原文件，浏览只读独立的轻量缩略图，并受 4-Worker 有界并发保护；
> 第二，**端侧微秒级检索**。基于 SQLite FTS5 为素材元数据建立倒排索引，支持在聊天中秒级引用本地材料；
> 第三，**真正的物理私密沙盒**。许多竞品只是在 UI 上弹个密码框隐藏，而我们对 Personal 私密空间采用了物理隔离的独立数据库文件。锁屏时执行四步优雅降维，清空内存、Checkpoint 事务并物理关闭句柄，做到了银行级的数据防泄漏。”

### 4. 深度防追问底稿
*   **极限追问 2.1**：“为什么不直接在同一个数据库里给敏感数据加个 `is_private = 1` 的字段，非要拆成两个物理数据库？”
    *   **最优回答**：“单库打标存在巨大的‘暗门风险’。一旦业务逻辑漏写 `WHERE is_private = 0`，或者出现 SQL 注入、全局模糊搜索，私密数据就会瞬间越权泄露；更致命的是，如果手机连上电脑通过 adb 导出单个 sqlite 文件，所有隐私一览无余。物理分库让私密数据拥有完全独立的文件加密和读写生命周期，在底层从物理层面彻底切断了越权查询的可能性。”
*   **极限追问 2.2**：“用户一次性选入 1000 张原图导入，手机低内存（RAM）场景下怎么保证不闪退（OOM）？”
    *   **最优回答**：“我们设计了 `MediaImportCommitBudget` 门禁与两阶段写入：第一阶段只探测文件 URI 的文件头和基本大小，快速完成体积账本校验（不读入内存）；第二阶段开启最多 4 个 Worker 的有界并发池，图片流按 Chunk 写入磁盘私有目录，生成缩略图后立即释放 Bitmap 内存引用，把整次导入的内存常驻开销压制在极其平缓的水平。”

## Slide 3: 双模长效记忆治理体系（伴聊 vs 长聊 彻底分开）

### 1. 页面视觉排版与插槽设计
*   **顶部标题区**：`BIFURCATED MEMORY ARCHITECTURE` | 双模长效记忆治理（伴聊拟人心智 vs 长聊严谨工程）
*   **主体左半屏（伴聊 IM 拟人记忆心智模型）**：
    *   **第一道门禁：“六记六不记”准入大筛网**：
        *   *坚决六不记*：瞬态动作（洗澡/吃撑）、闲聊垫话（哈哈/好的）、临时状态（等电梯/拿外卖）、未证实猜测、注入攻击、无意义碎片。
        *   *核心六必记*：核心画像、鲜明偏好、共同约定、深刻情感事件、重大里程碑、专属称谓。
    *   **三车道生命周期状态机**：
        *   `Working`（临时观察车道） $\rightarrow$ 跨会话多轮印证或置信度 $\ge 0.85 \rightarrow$ `Confirmed`（长期确信车道）；
        *   连续 5 次注入未被大模型采纳 $\rightarrow$ ACT-R 负反馈降权归档至 `Archive`。
    *   **艾宾浩斯衰减与突触强化**：普通事实随时间指数衰减；重要度 $\ge 8$ 的事实（过敏/生日）锁定 0.6 衰减铁底；MMR 多样性重排防复读。
    *   **夜间闭环**：`DiaryMemoryHarvester` 深夜提炼第一人称手账，次日生成 `TopicHook` 话题钩子。
*   **主体右半屏（长聊 Pro Chat 严谨工程记忆模型）**：
    *   **人工锁定快照（Confirmed Snapshot）**：固定世界观与人设骨架，无自然遗忘，永久绝对生效。
    *   **端侧混合检索（Hybrid RAG）**：SQLite FTS5 BM25 + 向量 RRF（倒数排名融合）算法，基准测试召回命中率达 **88.4%**。
    *   **表格零幻觉（Deterministic SQL Sandbox）**：未配置向量时，CSV/Excel 自动转为 SQLite 临时表只读 SQL 检索，彻底消灭复杂数字幻觉。
    *   **句子级防伪溯源**：输出带 `[S1]`, `[S2]` 引用角标，反向校验 SHA-256 签名，点击直达本地文档段落。
    *   **Git-like 分支隔离**：按分支树节点隔离记忆与摘要，A 分支推演绝不污染 B 分支。
*   **截图插槽**：
    *   `【插槽 3-A】`：白盒三车道记忆看板与夜间手账信封日记卡片截图（宽:高 = 16:9）。

### 2. 核心展示指标与参数
*   **废话过滤率**：大筛网拦截 95% 瞬态生理动作。
*   **RAG 召回率**：端侧混合检索（BM25 + 向量）Hit@3 达到 88.4%。
*   **防复读指标**：MMR 语义重叠惩罚，单话题记忆重复注入率归零。

### 3. 现场 60 秒最优演讲词
> “第三页是核心差异化设计 —— 双模长效记忆治理体系。
>
> 成熟竞品的记忆系统普遍是‘黑盒录音笔’，存在两大通病：要么把洗澡等废话全记成永久标签（像偷窥狂），要么刚聊完就机械复读。
>
> 我将两套场景的记忆系统彻底分开设计：
> 左边是**伴聊的拟人记忆**：通过‘六记六不记准入筛网’拦死瞬态垃圾信息；引入认知科学的 ACT-R 负反馈与艾宾浩斯衰减，普通小事自然淡忘，过敏生日锁死铁底；更重要的是，夜间自动收割手账日记，反哺次日开场。
> 右边是**长聊的严谨记忆**：面向严肃创作与工作。支持人工锁定设定快照，端侧混合检索命中率达 88.4%；遇到表格自动转 SQLite 只读 SQL 避免数字幻觉；且记忆严格按 Git-like 分支树隔离，推演剧情绝不串味。”

### 4. 深度防追问底稿
*   **极限追问 3.1**：“新提取的记忆如果和历史旧记忆冲突了（比如以前单身，现在有女友），算法具体怎么处理？”
    *   **最优回答**：“我们不搞静默覆盖，也不全盘推给大模型黑盒处理。首先，输入给对齐模型的只有当前相关的至多 8 条旧记忆候选；模型只能输出原子操作标记。更重要的是，在代码层设立了 Sanitizer 物理防线：置信度低于 0.78 拒绝修改；凡是用户手动录入的 manual 记忆，代码层直接拦截任何 AI 的覆写指令，并触发 `ask_before_action` 反问契约，让角色在下一轮自然向用户求证，保护数据绝对安全。”
*   **极限追问 3.2**：“端侧混合检索（FTS5 + 向量）为什么能做到 88.4% 命中率？基准测试是怎么测的？”
    *   **最优回答**：“这是我们在做材料库时搭建的离线 Benchmark：针对 3 篇世界观设定切为 45 个 Chunk（每块 800 Token），人工构造了 50 个含标准答案的问答对。实测发现：纯 BM25 面对口语同义词表现弱（64%），纯向量面对专有名词容易泛化模糊（76%）。我们在端侧通过 RRF 算法将两者打分融合，既保住了专有名词的精确命中，又兼顾了口语语义泛化，最终 Top-3 召回率达到 88.4%。”

## Slide 8: 双泳道流式渲染与长文本视口防抖（Viewport & Rendering Dynamics）

### 1. 页面视觉排版与插槽设计
*   **顶部标题区**：`STREAMING RENDERING & ANTI-JITTER` | 双泳道流式渲染与超长会话视口防抖工程
*   **主体左侧（双泳道隔离与思考流微预览架构）**：
    *   **双泳道彻底物理隔离**：思考过程（Reasoning）与正文输出（Content）分入两个独立的 React 渲染表面，思考流折叠展开不触发正文树重绘。
    *   **思考流 7 行微预览防抖**：
        *   字号 14px、行高 23px，设定 7 行上限 161px 视口；
        *   **300 字符量化步长与 $\pm 4\text{dp}$ 高度稳定器**：彻底消除单字符换行导致的容器高度跳动与浮点微抖；
        *   **首尾 24dp 渐变淡出遮罩（Dual Fade）**：文字在遮罩背后平滑向上卷，视觉零突跳。
    *   **单阶段原子展开锁（Single-stage Expand Lock）**：展开时先锁定滚动视口，待全量文本原生测量完成一次性平滑展开，移除伪垫高层，主页面零全屏 Re-render。
*   **主体右侧（长文本视口防抖与海量消息性能）**：
    *   **原生视口维持（Maintain Visible Position）**：底层配置 `autoscrollToBottomThreshold: 250`。当用户向上翻看历史超过阈值时，屏幕物理锁死不动，新字在屏幕外静默渲染，**彻底根除误吸底与页面剧烈震颤**。
    *   **EMA 速率打字机平滑引擎**：指数移动平均实时估算吐字速率，网络断流积压少于 12 字符时以 0.6~1.0 字符/帧平稳滑行（巡航地板），绝不突然卡死急停。
    *   **6000+ 条超长消息 Keyset 游标合并**：抛弃慢查的 `OFFSET/LIMIT`，采用复合游标 `(createdAt, id)` 在 O(n) 时间内单次有序归并，避免反复全量数组排序。
*   **截图插槽**：
    *   `【插槽 8-A】`：思考流 7 行微预览折叠卡片与超长列表滚动效果截图（宽:高 = 16:9）。

### 2. 核心展示指标与参数
*   **帧率表现**：万字流式出字 + 向上翻看历史，列表帧率稳定在 **58 ~ 60 fps**。
*   **重绘降低**：双泳道与原子锁优化后，流式生成时历史气泡重绘率降低 **95%**。
*   **列表容量**：单会话 6000+ 消息流畅加载，首帧定位无白屏。

### 3. 现场 60 秒最优演讲词
> “第八页展示的是移动端工程体验最深水区的突破 —— 双泳道流式渲染与长文本视口防抖。
>
> 很多 AI 软件在大模型吐字时，用户如果向上滑看历史，页面会被新字疯狂拉回底部，或者因为每秒文字换行导致屏幕疯狂抽搐。
>
> 我们做了三项极客级体验打磨：
> 第一，**双泳道隔离**。将思考流与正文隔离在独立渲染表面，思考框折叠展开绝不引发正文重绘；
> 第二，**7 行微预览抗抖**。通过 300 字符量化步长与首尾 24dp 渐变遮罩，文字在遮罩下平滑卷动，彻底消除了每秒跳行的视觉抽搐，点击展开使用单阶段原子锁，零位移跑飞；
> 第三，**原生视口锚定**。开启底层原生位置维持，用户翻阅时视口物理钉死不动，配合 EMA 打字机平滑算法，在 6000 多条消息下依然保持 60fps 丝滑阅读。”

### 4. 深度防追问底稿
*   **极限追问 8.1**：“为什么很多现成的第三方聊天库（如 GiftedChat）做不到这种防抖，你们的本质区别在哪？”
    *   **最优回答**：“第三方库大多是在 JS 线程通过 `onContentSizeChange` 监听高度，然后调用 `scrollToEnd`。在大模型每秒 50 个高频 Token 冲击下，JS 线程的测量事件和用户的触摸滚动事件在 Bridge 两端发生严重竞态死锁，导致视口像打架一样上下狂跳。我们彻底废弃了 JS 竞态定时器，直接在原生底层启用 `maintainVisibleContentPosition`，滚动锚定完全由原生渲染管线托管，从根本上消除了 Bridge 延迟引起的跳屏。”
