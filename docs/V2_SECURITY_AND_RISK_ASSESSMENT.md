# Pixory V2 安全与性能风险审计

本文记录了对视频集成模块和底层原生逻辑审计中发现的关键风险点。目前系统在物理隔离和基础流程上结构清晰，但在处理大文件、磁盘极值和后台强杀等边缘场景时仍有漏洞。

## 1. 内存溢出风险 (OOM)

### 备份导出时的 Base64 加载
在 `backupService.ts` 中，使用 `FileSystem.readAsStringAsync(..., { encoding: Base64 })` 复制备份包会导致全量文件进入内存。
*   **后果**：对于 V2 涉及的 GB 级视频，JS 堆内存会瞬间溢出导致应用崩溃。
*   **建议**：原生层 (Kotlin) 需提供分块流式复制接口，避免一次性读入。

### 视频封面生成的 Native 内存占用
`PixoryMediaModule.kt` 调用 `getFrameAtTime` 提取封面。
*   **风险**：处理 4K/8K 或编码非标视频时，Native 层申请的大块内存溢出无法在 JS 端捕获。
*   **优化**：优先使用 `getScaledFrameAtTime` 限制位图尺寸，并增加原生异常处理。

### 桥接线程阻塞
部分原生方法（如 `saveVideoToMediaStore`）在主线程同步执行大文件写入循环，未进行异步分流。
*   **问题**：写入 GB 视频会霸占桥接线程，导致 JS 与原生通讯死锁，UI 进度停止更新，应用出现 ANR。
*   **修复**：长耗时 IO 必须强制调度到后台协程（IO Dispatcher）中执行。

## 2. 存储泄露与数据一致性

### 导入失败导致的“幽灵文件”
导入流程中，文件先移动到 `originals/` 后才写数据库。
*   **风险**：若落库前崩溃，文件将留在沙盒目录且无法被现有清理逻辑追踪，长期积累会浪费大量磁盘空间。
*   **自愈**：需实现孤立文件扫描器，定期对比数据库记录与物理文件，清理无主资源。

### 磁盘空间耗尽拦截
`copyUriToFileWithProgress` 未做前置空间检查。写入中途触发 `ENOSPC` 会导致 I/O 报错并可能引发系统卡顿。建议在写入前对比文件大小与剩余磁盘空间。

### 迁移与导入的原子性
`importEncryptedPersonalPack` 缺乏事务包裹和失败清理逻辑。导入中断会留下残缺的数据库记录和碎片文件。

### MediaStore 导出占位残留
Android Q+ 使用 `IS_PENDING = 1` 时，若写入抛错但未手动销毁 `destinationUri`，相册会出现无法打开的损坏文件。

## 3. 其它技术风险

*   **视频旋转丢失**：`getVideoMetadata` 漏读了旋转标签。需检测 90/270 度旋转并自动互换宽高，否则 UI 渲染会变形。
*   **异步解析的回调安全**：视频切换时，若在解析完成前组件已卸载，后续的 `play()` 调用可能导致背景发出不明声音。需在回调中校验挂载状态。
*   **强杀导致进度丢失**：当前播放进度仅在卸载时保存。建议引入 `AppState` 监听或节流定时落库，防止强杀应用导致进度重置。
*   **解压炸弹防范**：原生解压应限制输出流的体积上限，防止恶意高压缩比文件撑爆存储。
*   **隐私缓存残留**：查看隐私包产生的临时明文文件在强杀后可能存留。建议在应用冷启动或退出隐私模式时强制擦除 `temp/`。
