# AI 聊天“日常陪伴”模式设计

## 文档状态

- 设计状态：已确认，可进入实施计划
- 产品范围：Pixory AI 聊天模块大更新第一版
- 对外名称：`沉浸对话`、`日常陪伴`
- 内部建议枚举：`immersive`、`companion`
- 平台优先级：Android 优先

## 目标

在现有长回复、情景扮演能力之外，增加一种接近日常即时通信的陪伴体验。它不依赖 AI 主动推送，而是通过自然的短消息形态、可连发的语义节奏、克制的等待反馈和更沉浸的聊天表面，让用户感到“对方正在和我聊天”，而不是“系统正在生成一篇回答”。

本次更新同时整理现有聊天顶部入口，并把多条 AI 消息能力建设为共享能力：日常陪伴模式默认使用，沉浸对话模式在模型明确返回多消息协议时也可使用。

成功标准：

- 用户能理解两种模式的差异，并可随时切换、随时切回。
- 老会话升级后保持原样，不被强制改成日常陪伴模式。
- 日常陪伴回复可自然地只发一条，也可根据语义和情绪连发多条。
- AI 连发期间可被用户打断，已显示内容保留，未显示内容不会污染后续上下文、搜索或记忆。
- 模式切换、停止、失败、切后台、路由切换和进程恢复均不会造成旧回复串入新会话。
- 聊天顶部更简洁，查找聊天记录仍可被稳定找到。

## 设计原则

1. **共享聊天核心**：不新建第二套聊天系统；复用现有会话、分支、记忆、资料、引用、模型配置和生成恢复能力。
2. **模式决定下一轮，不改写历史**：会话保存当前模式，每条消息保存生成时的模式快照。
3. **语义决定分条**：不要求固定条数、固定字数或情绪枚举；避免为了“像微信”而机械拆句。
4. **模型决定内容，客户端决定呈现**：模型只表达消息边界，不输出毫秒、节奏参数或动画指令。
5. **可见内容才是历史**：未显示的队列片段不得进入对话上下文、搜索、摘要或记忆。
6. **参考即时通信节奏，不复制微信品牌**：不引入微信绿、不照搬全部界面、不制造在线状态或已读回执。
7. **优先可靠，再追求拟人**：任何解析、并发和生命周期异常都必须安全退化成可阅读、可重试的状态。

## 模式语义与兼容规则

### 会话与消息的模式归属

- `ai_threads.chatMode` 表示该会话下一轮默认使用的模式。
- `ai_messages.modeSnapshot` 表示该消息产生时使用的模式。
- 历史消息始终按自身快照渲染，不读取会话当前模式来改外观。
- 切换模式后，不重新生成、不重新拆分、不重新着色已存在消息。
- 用户新发的一轮使用会话当前模式。
- 对旧 AI 消息执行“重新生成”或“继续”时，使用该 AI 消息的原始模式快照，避免同一版本链混入另一种表达协议。
- 对某条旧用户消息创建新的分支回复时，默认使用当前会话模式，并在新 AI 父消息上保存新的模式快照。

### 老会话与新会话

- 数据库迁移将所有既有会话和既有消息补为 `immersive`，保证升级后外观与回复方式不变。
- 不在每次进入会话时弹窗询问模式。
- 升级后第一次进入聊天页时，在输入区模式按钮附近显示一次非阻塞提示：“可切换沉浸对话或日常陪伴，之后也能随时切回。”
- 提示只出现一次，可点空白处关闭，不阻止输入，不要求用户先做选择。
- 新会话不增加独立选择页。空会话中模式按钮保持可见，用户可在第一条消息前选择；未选择时沿用产品默认的 `沉浸对话`。
- 侧边抽屉及其新建会话入口完全不改。

### 生成期间切换

- 空闲时切换立即作用于下一轮，并持久化到会话。
- 已有请求生成或连发队列正在播放时，当前 AI 回合继续按它的 `modeSnapshot` 完成；模式按钮可立即显示用户刚选的新模式，并用轻提示说明“下一轮生效”。
- 页面当前正在演出的回复仍使用该回合快照决定标题状态、队列和气泡行为；结束、停止、失败或被新用户消息打断后，页面进入新会话模式。
- 如果用户切换后立刻发消息，新消息先打断旧回合，再按新模式启动生成。
- 切换动作本身不取消生成，不允许旧模式的延迟回调写入新回合；所有回调继续校验 `threadId + messageId + generationId`。
- 快速连续切换采用“最后一次用户选择生效”。会话模式写入必须按会话串行化，或使用仅存在于客户端控制面的选择 revision 丢弃过期完成回调，不能让较早的异步写入最后覆盖较新的选择。
- 模式选择 revision 只用于 UI/持久化竞态控制，不进入数据库业务语义、prompt、记忆、摘要、provider cache key 或缓存观测家族。

## 入口与页面结构

### 输入区模式按钮

模式入口放在现有输入框工具栏，位于模型入口和 AI 帮答之后，采用紧凑文字按钮：

- `沉浸⌄`
- `日常⌄`

交互规则：

- 点击后打开轻量选择面板，只显示两种模式及一句差异说明。
- 当前模式有选中状态；再次选择当前项只关闭面板。
- 按钮低频但始终可见，不占用已经拥挤的顶部。
- 文案不使用“微信模式”作为正式产品名，降低品牌依赖；设置说明可用“像日常即时聊天一样自然连发”解释。
- 按钮、面板、选中态和触控尺寸使用共享 design tokens，不在页面内散落硬编码尺寸。

### 顶部精简

顶部调整为：

```text
[现有抽屉按钮]       [会话标题 / 模型]       [•••]
```

- 移除顶部搜索图标。
- 移除顶部新建聊天图标；侧边抽屉已有新建入口，避免同屏重复。
- 左侧只保留现有抽屉按钮，抽屉内容与行为不改。
- 右侧使用 `ellipsis-horizontal`，视觉尺寸 24dp，保留现有 40×40dp 按钮容器，并用 `hitSlop` 扩充到接近 48dp 的可触区域。
- 三点节奏参考微信的横向留白，但继续使用项目现有 Ionicons 和颜色体系。
- 点击三点直接进入现有会话设置，不再增加一层菜单。
- 左右区域保持等宽占位，避免移除按钮后标题视觉偏移。

### 查找聊天记录

在“会话设置 → 当前会话”中，将 `查找聊天记录` 放在 `会话名称` 之后：

1. 会话名称
2. 查找聊天记录
3. 会话模型
4. 会话资料库（符合现有条件时）
5. 创作路线树

入口直接复用现有聊天搜索路由、搜索结果定位和目标消息跳转，不新建页面、不改变搜索数据范围。

### 顶部文字与“正在输入”

- 会话标题改为现有系统无衬线字体，不引入新字体。
- 标题建议为 `18sp / 600 / 24` 行高，替换当前 Android 上偏大、偏细的 `20sp / 400` 衬线覆盖。
- 模型副标题沿用现有 caption 层级。
- 日常陪伴回合从请求进入生成开始，到最后一条队列消息显示完成为止，主标题替换为 `对方正在输入…`。
- 该状态只覆盖会话名称，模型副标题保留；停止、失败、空响应、路由离开、旧任务失效或最后一条显示后立即恢复会话名称。
- `对方正在输入…` 是静态文字状态，不带跳动点，不使用 `AiTypingIndicator`。
- 沉浸对话模式继续使用现有生成反馈，不把顶部标题替换成该文案。

## 日常陪伴视觉规则

- 日常陪伴模式的聊天页画布和顶部背景统一为 `#EDEDED`。
- `#EDEDED` 必须进入共享颜色 token，再由聊天页引用；不得在多个组件中重复写字面量。
- 输入区/Composer 继续作为当前独立表面，不跟随画布变成同色，从而保持输入焦点和页面层次。
- 沉浸对话模式颜色完全不变。
- 不新增微信绿色发送气泡，不重做现有 `AiMessageBubble`，继续使用当前用户/AI 气泡、头像、圆角和操作能力。
- 日常陪伴模式不在每个 AI 气泡上方重复显示名称。
- 头像逻辑沿用现有角色与会话配置；未开启头像时不为“像微信”而强制增加。
- 引用、附件、失败重试、收藏、分支、编辑等现有能力继续存在，必要操作仍挂在对应父回合上。
- 页面外壳使用明确的 `presentationMode`：存在活动回合时取该回合的模式快照，无活动回合时取会话当前模式。这样生成期间切换只保存“下一轮模式”，不会让当前页面底色、标题状态或回复演出中途突变。

## 消息内容协议

### 统一多消息格式

两种模式共用最小协议：

```xml
<messages>
  <msg>你！</msg>
  <msg>好！</msg>
  <msg>啊！</msg>
  <msg>啊！</msg>
</messages>
```

协议只表达“这是同一 AI 回合中的多条消息”以及每条消息的边界。

不得加入：

- `pace`、`delay` 或毫秒字段；
- 固定情绪枚举；
- 固定消息条数；
- 每条固定字数；
- 动画或 UI 指令。

### 提示词方向

日常陪伴模式增加独立且克制的风格说明：

```text
当前是日常陪伴式聊天。请像日常即时聊天一样自然回应，先理解对方此刻的情绪和意图，再决定语气、长短以及发一条还是多条。激动、转折或补充时可以自然连发，但不要为了分条而分条。除非用户明确要求，不使用标题、列表或大段书面结构。

输出必须使用 <messages> 根标签，每条准备单独发送的消息放在一个 <msg> 中。只输出协议内容，不解释协议。
```

角色卡、安全边界、资料引用、记忆和当前用户请求仍由现有 prompt assembly 提供。两种模式共用的防污染规则进入稳定 system 前缀；具体模式提示只进入当前轮 user prompt 尾部，不覆盖角色身份，也不能被资料内容修改。

沉浸对话模式不强制使用协议；只增加一句能力说明：当语义确实适合连发时，可以使用同一 `<messages>` 协议，否则保持现有普通 Markdown 回复。

模式是表达偏好，不是内容能力上限，也不允许客户端静默替用户切换模式：

- 用户明确要求完整攻略、代码、表格、长文、严谨分析或逐步说明时，完整性优先于短碎感；日常陪伴模式仍保持当前模式，但应使用一个完整 `<msg>`，或少量语义完整的 `<msg>`，回答后继续留在日常陪伴模式。
- 代码围栏、Markdown 表格、公式、链接、引用段和引用标记属于不可拆分的原子内容，不得从中间切成多个气泡；emoji 与组合字符也不得被按字符截断。
- 每个 `<msg>` 继续交给现有 `AiMessageContent` 渲染，因此用户明确需要时仍可在日常陪伴气泡中使用 Markdown 和代码块；“少用 Markdown”只是不主动套模板，不是禁用能力。
- 客户端不根据字数做二次语义拆分。模型给出的边界合法时原样保留，协议异常时宁可回退成一个完整气泡，也不冒险把代码、链接或句子拆坏。

### AI 是否知道用户连发了多条

日常陪伴模式会把短时间内的连续用户消息作为一个“用户消息组”交给同一次生成：

- 每条用户消息在点击发送后立即独立持久化和显示，不能等收集结束再保存。
- 第一条发送后开启 800ms 静默窗口；窗口内新消息到达则重新计时。
- 从第一条起最多等待 2.4 秒，达到上限后立即封组，避免用户感到发送被卡住。
- 组装 prompt 时保留消息顺序和消息边界，例如以“用户刚刚连续发送了以下消息”包裹，而不是把文本无分隔拼接。
- 同一组只触发一个 AI 父回合，因此 AI 能理解“你！/好！/啊！”是连续情绪，而不是四个互不相关的问题。
- 附件消息、明确的停止动作、会话切换或达到最大等待时间会立即封组。
- 已持久化的组内用户消息只作为本轮 current turn 输入一次；组装 provider history 时必须排除本组 `userMessageIds`，避免同一内容同时出现在 history 和当前用户消息中。
- 连续消息收集开始时即固定本轮 `modeSnapshot=companion`。收集期间切到沉浸对话会立即封组并仍用日常陪伴完成这一轮，新模式只影响再下一轮。
- 沉浸对话模式第一版不额外引入用户消息收集延迟，保持现有发送行为。

800ms 与 2.4 秒是客户端体验常量，必须集中定义并可测试，不进入模型提示词。

### 模式切换、历史上下文与高缓存

现有请求的真实顺序是 `systemPrompt → history → current userPrompt`。历史消息通常比角色指令占用更多 token，因此模式隔离不能靠改写整段 system 或逐条包装历史完成，否则每次切换都会破坏可增长的历史前缀缓存。

采用以下结构：

```text
两种模式共用的稳定 system 前缀
→ 原样、按顺序增长的历史消息
→ 当前用户消息
→ 当前轮 presentationMode 指令与输出协议
```

- 新增独立 `presentationMode`，不得复用项目现有表示 `companion / roleplay / knowledge / personal` 的 `AiChatMode`。
- 稳定 system 只增加两种模式共用的规则：Pixory 会在当前轮末尾声明回复协议；历史回复的长度、分条和排版只代表历史内容，不构成当前轮格式指令。
- 具体的 `沉浸对话` 或 `日常陪伴` 指令只追加到当前 user prompt 的末尾，位于历史之后。切换模式时，前面的 system 与全部历史 token 保持不变，只让当前轮动态后缀分叉。
- 历史用户消息和已显示 AI 正文原样进入 provider history；不按模式重写、不逐条添加标签、不加入模式 system 消息。只有父消息中已物化的 revealed 内容可进入历史。
- 时间戳、切换时间、切换次数、`modeEpoch`、请求 ID、`generationId`、随机数、演出延迟和气泡数量不得进入提示词或稳定缓存键。
- `presentationMode` 必须进入完整回复缓存、精确缓存和观测维度，防止跨模式复用最终答案；provider 的前缀缓存应尽量复用两种模式共同的真实 token 前缀，不能用无必要的切换序号制造新缓存家族。
- 稳定记忆快照只在事实内容真正变化时更新；切换模式、改变分条数量或页面生命周期不得更新 `memoryEpoch`。
- 记忆提取和摘要不得记录产品模式、AI 气泡数量、Markdown 结构、输入状态或演出节奏。用户在正文里明确表达的沟通偏好仍可作为用户偏好保存，但会话的 `presentationMode` 始终拥有当前轮格式优先级。
- 缓存观测至少记录 `presentationMode`、`modeSwitchedThisTurn`、`stablePrefixHash`、`historyPrefixHash`、`historyPrefixEstimatedTokens`、`historyMessageCount`、`totalPromptTokens`、`cachedInputTokens`、`cachedTokenRatio`、`memoryEpochChanged` 和 `cacheMissReason`。history hash 只用于证明模式切换没有改写已发送历史，不进入提示词或 provider cache routing key。

这套结构允许切换后的第一轮在动态尾部使用新协议，同时继续复用共同 system 和历史前缀。若 provider 只支持较粗粒度的前缀缓存，正确模式仍优先于命中率，不允许为了命中而让两种输出协议同时生效。

## 解析与展示流水线

### 输出分类

沉浸对话模式：

- 忽略开头空白后，输出以 `<messages>` 开始时进入多消息缓冲和解析。
- 其他输出立即回到现有 Markdown 流式显示和 tail replay，不因新增协议降低普通长回复的实时性。
- 分类完成前只短暂缓存识别前缀；判定为普通文本后将缓存前缀原样交回现有流式管线。

日常陪伴模式：

- provider 仍可采用流式网络请求，但 UI 不逐 token 显示。
- 完整响应先进入非可见缓冲，终态后统一解析为消息片段，再进入逐条显示队列。
- 这种设计保证格式异常时可以安全回退为一个干净气泡，也避免半个 XML 标签或半句话出现在界面。
- provider 生成期间以及队列播放期间，顶部都保持 `对方正在输入…`。

### 解析规则与兜底

- 允许根标签前后有空白。
- 忽略空 `<msg>`，保留非空消息原有顺序。
- 对合法 XML 实体进行解码，但不把消息正文当 HTML 渲染。
- 根标签缺失、标签未闭合、嵌套错误或没有有效 `<msg>` 时，清理已知协议标签并把可读正文作为一个气泡显示。
- 协议标签和解析错误详情永远不直接展示给用户。
- 如果清理后仍为空，则进入“空响应”失败状态并提供重试。
- 模型不受固定条数约束；客户端仅做异常防护：单个 AI 回合最多演出 20 个气泡，超过部分按原顺序合并到第 20 个气泡中。该上限不进入提示词，不改变正常语义。

### 连发节奏

- 每条消息以完整气泡出现，不做逐字打字机。
- 用户消息点击发送后立即落屏；连续消息封组并创建请求后，顶部立即切换为静态`对方正在输入…`，让用户始终知道请求已被接收。
- provider 请求本身已构成主要思考等待；当 provider 用时不足 1.5 秒时，解析完成后首条增加 250–600ms 的轻微随机停顿；当 provider 已用时达到 1.5 秒时，首条不再附加人为等待，避免“生成已慢还要继续装忙”。
- 后续条目间增加 350–900ms 的随机停顿。
- 不按每个字符模拟长时间输入，不让短回复演出时间超过真实生成时间太多。
- 同一回合全部额外演出等待累计最多 6 秒；达到上限后剩余气泡缩短间隔继续显示，不能让用户等待几十秒。
- 随机值由客户端生成并集中配置；测试注入固定随机源，避免脆弱测试。
- 日常陪伴模式不显示气泡内三点动画；等待反馈只使用顶部静态文字。
- 节奏完全由客户端控制，provider 或模型不得输出 delay/pace；服务端只负责返回内容。网络断开、切后台或进程恢复时不尝试重演“真人节奏”，优先保证消息完整和状态可恢复。

### 沉浸对话中的多消息

- 普通文本继续走现有 Markdown、流式显示和 tail replay。
- 只有明确以 `<messages>` 开始的响应才进入分段展示。
- 分段响应复用同一解析器、父回合和片段数据结构，但保持沉浸对话现有画布、标题和操作样式。
- 沉浸对话分段等待时可沿用现有生成反馈；“不使用三点动画”的限制只针对日常陪伴模式。

## 用户打断与并发规则

当日常陪伴 AI 正在请求或仍有未显示片段时，用户再次发送消息：

1. 立即持久化并显示新用户消息。
2. abort 旧 provider 请求，并使旧 `generationId` 失效。
3. 保留旧回合已经显示的片段。
4. 将旧回合尚未显示的片段标记为 `discarded`。
5. 用已显示片段重建旧父消息 `content`，旧父消息终态记为 `stopped`。
6. 搜索、摘要、记忆和下一轮 prompt 只能读取已经显示的片段。
7. 对新用户消息执行连续消息收集；封组后创建新的 `generationId` 并开始生成。

任何旧请求的晚到 patch、终态回调或队列定时器都必须同时核对 `threadId`、父 `messageId` 和 `generationId`；不一致时静默丢弃，不能插入提示、错误或消息。

用户主动点击停止与用户插话打断使用相同的“保留已显示、丢弃未显示”底层操作，但只在用户插话时自动启动下一轮。

## 状态机与触发清单

### 状态优先级

同一时刻可能存在会话模式、生成、页面生命周期和模式切换状态。UI 按以下优先级决策：

1. 路由已离开或组件卸载：不再更新当前页面。
2. `generationId` 失效：丢弃回调。
3. 日常陪伴回合正在生成或演出：顶部显示 `对方正在输入…`。
4. 回合进入终态：恢复会话标题。
5. 无活动回合：按会话当前模式渲染画布与输入区模式按钮。

### 主状态表

| 状态 | 触发 | 用户可见表现 | 数据/系统动作 | 退出条件 |
| --- | --- | --- | --- | --- |
| `idle` | 页面加载完成且无活动请求、队列 | 会话标题；可输入、切模式 | 读取会话模式与历史消息快照 | 用户发送、重试、重新生成或恢复任务 |
| `collecting_user_burst` | 日常陪伴模式发送第一条用户消息 | 用户消息立即出现；无三点动画 | 持久化每条消息；800ms 静默窗口，最多 2.4 秒 | 静默到期、到达上限、附件/导航等强制封组 |
| `queued` | 用户消息组封组 | 顶部切为`对方正在输入…` | 创建 AI 父消息和 `generationId`，准备 prompt | provider 请求开始或前置校验失败 |
| `provider_generating` | provider 接受请求 | 顶部保持`对方正在输入…` | 父 `deliveryState=buffering`；网络流写入非可见缓冲；校验 generation 身份 | provider 完成、停止、失败、用户打断、路由失效 |
| `output_classification` | 收到足够前缀或 provider 完成 | 日常陪伴无新增气泡 | 判断普通文本或 `<messages>` 协议 | 进入现有流式管线、分段解析或回退 |
| `buffering_segment` | 日常陪伴响应未到终态，或沉浸模式已识别协议 | 只显示对应模式的等待反馈 | 缓冲原始协议，不写入可见父内容 | provider 完成、失败或停止 |
| `segment_queued` | 完整响应解析出有效片段 | 顶部保持输入状态 | 同一事务持久化有序片段为 `queued` 并设置 `deliveryState=ready` | 首条等待开始、被打断或恢复策略直接完成 |
| `waiting_first_segment` | 队列非空且尚未显示 | 顶部输入状态 | 等待 250–600ms，计入 6 秒总预算 | 计时结束、停止、用户打断、页面后台化 |
| `revealing_segment` | 当前片段到达显示时刻 | 完整气泡一次出现 | 事务更新片段为 `revealed`，同步父 `content` | 持久化成功、失败或身份失效 |
| `between_segments` | 仍有 queued 片段 | 顶部继续输入状态 | 等待 350–900ms，并检查预算与 generation | 下一条显示、停止、用户打断、后台化 |
| `completed` | 最后一片段已显示并持久化 | 恢复标题；显示完整操作能力 | 父消息状态为 `completed`、`deliveryState=terminal`；触发后续搜索/摘要/记忆资格 | 返回 `idle` |
| `stopped_before_visible` | 在首条显示前停止或被打断 | 恢复标题；显示可重试的停止态 | 丢弃全部 queued 片段；父内容为空，状态 `stopped` | 用户重试或继续聊天 |
| `stopped_after_partial` | 已显示至少一条后停止或被打断 | 已显示气泡保留；恢复标题；父回合显示停止态 | 未显示片段 `discarded`；父内容只含已显示片段 | 用户重试或继续聊天 |
| `failed_before_visible` | provider、解析持久化或前置校验在首条前失败 | 恢复标题；错误与重试入口 | 父状态 `failed`，不产生可搜索正文 | 用户重试或继续聊天 |
| `failed_after_partial` | 片段已显示后发生持久化/队列错误 | 已显示气泡保留；恢复标题；紧凑失败提示 | 未显示片段丢弃；父内容只含已显示片段，状态 `failed` | 用户重试或继续聊天 |
| `parse_fallback` | 协议缺失或损坏但清理后有正文 | 按当前模式显示一个干净气泡 | 不保存协议标签；创建单个片段 | 片段显示完成或持久化失败 |
| `empty_response` | provider 成功但清理后无正文 | 恢复标题；“未收到有效回复，请重试” | 父状态 `failed`，记录内部错误类别 | 用户重试或继续聊天 |
| `stale_generation_discarded` | 回调身份与活动 generation 不一致 | 无新增 UI、无 toast | 静默丢弃回调和定时器 | 无；保持当前有效状态 |
| `background_detached` | App 进入后台或聊天路由离开 | 当前页不可见 | 取消前台演出计时；持久化父/片段状态；请求可按现有管理器继续 | 回前台、请求终态或进程结束 |
| `resumed` | 页面重新订阅活动任务 | 根据持久化状态恢复 | 若后台已完成则立即显示全部已完成片段；若仍生成则恢复顶部状态；不重演已错过延迟 | 转入生成、队列或完成状态 |
| `orphan_recovered` | 启动时发现无活动任务对应的 `generating` 消息 | 不永久显示输入状态；完整回复直接出现，不完整回复提供重试 | `ready/revealing` 的完整片段跳过延迟完成；仅 `buffering` 的不完整任务转失败并清理未完成缓冲 | 返回 `idle` |
| `pending_mode_switch` | 活动回合中用户选择另一模式 | 按钮显示新模式并提示“下一轮生效”；当前回合外观不突变 | 持久化会话新模式；当前回合继续使用快照 | 当前回合终态或被新消息打断 |

| --- | --- | --- | --- |

| 收集用户连续消息 | 会话名称 | 保留 | 无 |
| queued / provider 生成 / 分段缓冲 | `对方正在输入…` | 保留 | 无 |

## 时间标签

日常陪伴模式使用独立的即时通信时间策略，普通模式保留当前按日期分隔的逻辑。

显示条件：

- 当前消息或消息组与上一条可见消息的间隔小于 5 分钟：不显示时间。
- 间隔达到 5 分钟：在当前消息或消息组前显示一个居中时间标签。
- 会话第一条可见消息始终显示时间。
- 一个 AI 多气泡父回合只评估一次时间，不在每个子气泡前重复。
- 同一用户连续消息组也只在组首评估一次。

格式：

- 同一天：只显示时间。
- 超过一天但不足一周：显示日期与时间。
- 超过一周：只显示日期。
- 文案使用设备本地时区和现有本地化能力，不把格式硬编码为单一地区字符串。

分页与历史加载：

- 时间标签是从按时间升序的可见消息/消息组派生的展示项，不作为聊天消息单独持久化。
- 加载更早分页后，从新增边界重新计算相邻间隔，不能出现重复标签。
- `discarded` 片段和空失败父回合不参与时间计算；部分显示的父回合按已显示的组首时间参与。

## 数据模型与持久化

### 会话与消息字段

建议迁移：

```text
ai_threads.chatMode
  'immersive' | 'companion'
  NOT NULL DEFAULT 'immersive'

ai_messages.modeSnapshot
  'immersive' | 'companion'
  NOT NULL DEFAULT 'immersive'

ai_messages.deliveryState（仅 assistant 父回合使用）
  'none' | 'buffering' | 'ready' | 'revealing' | 'terminal'
  NOT NULL DEFAULT 'none'
```

`deliveryState` 与既有消息状态分工：既有 `status` 表示请求/消息终态，`deliveryState` 表示多气泡回复是否已完成解析以及是否仍有待显示内容。消息版本也必须保存 `modeSnapshot`，保证切换历史版本、重新生成和分支查看时不丢失原模式。

### 父回合与片段

保持一个 assistant `ai_messages` 父回合承载现有语义，在其下保存多个有序片段：

```text
ai_messages (assistant parent turn)
└─ ai_message_segments
   ├─ id
   ├─ messageId
   ├─ ordinal
   ├─ content
   ├─ status: queued | revealed | discarded
   ├─ createdAt
   └─ revealedAt
```

- 父回合继续拥有 provider/model、generation、branch、version、favorite、citation、reasoning、错误和完成状态。
- 片段只负责同一回合内部的展示顺序与可见性，不成为独立分支节点。
- `messageId + ordinal` 唯一，片段状态只能从 `queued` 进入 `revealed` 或 `discarded`，不能从 `discarded` 复活。
- 每次显示片段时，在同一事务内将其改为 `revealed`，并把父 `content` 更新为所有 revealed 片段按序用 `\n\n` 连接的兼容文本；该分隔符固定且不带模式、时间或 UI 元数据。
- queued/discarded 内容不进入父 `content`。
- 解析前的原始协议缓冲不写入父 `content`、搜索表或 prompt 快照；进程死亡时允许丢弃未完成缓冲并转为可恢复失败。
- provider 完成并成功解析后，必须在同一事务中写入全部 queued 片段并把父 `deliveryState` 改为 `ready`；这是区分“回复已完整落库，只差演出”和“请求中途死亡”的持久化标记。
- 消息版本快照必须同时保存有序片段和模式快照；采用关联版本片段表或版本快照字段均可，但恢复版本后必须得到相同气泡边界。
- 引用默认仍归父回合；如果后续需要精确到片段，可另做扩展，第一版不增加引用归属复杂度。

### 可见性边界

以下消费者只读取父 `content` 或 `revealed` 片段：

- 下一轮对话历史；
- 聊天搜索；
- 会话摘要；
- 长短期记忆提取；
- 会话预览；
- 导出与备份中的用户可见正文。

queued/discarded 片段不得被任何上述消费者读取。父消息状态为 `stopped` 或 `failed` 但已有 revealed 内容时，消费者可按现有产品规则决定是否纳入；无论如何只能读取已显示文本。

### 生命周期与恢复

- App 进入后台时，不依赖 React 组件计时器继续连发。
- 已解析片段及其状态立即存 SQLite；前台计时器暂停。
- 请求在后台完成且 JS 仍运行时，解析并持久化 queued 片段并标记 `ready`，但不逐条演出；返回前台后跳过延迟，在一个恢复事务中把剩余 queued 片段改为 revealed、物化父内容并立即显示。
- 返回前台时若请求仍由现有 generation manager 管理，恢复订阅和顶部状态；已显示片段不得重复动画。
- 进程被杀后，启动恢复任务检查父消息和片段：`deliveryState=ready|revealing` 且存在完整 queued/revealed 片段时，跳过演出延迟并安全完成；只有仍为 `buffering`、没有完整解析标记且没有活动请求支撑的 `generating` 父消息才转为可恢复失败。失败时 revealed 保留，queued 改为 discarded。
- 任何恢复写入必须受 Personal space 与 normal space 边界约束，不跨空间查询或合并。

### 列表、滚动与现有流式链路隔离

- 不创建第二个聊天列表，也不把每个片段插成独立 `FlatList` item。一个 assistant 父回合始终对应一个稳定的列表项和 `message.id` key，多个 revealed 片段只在该列表项内部渲染为多个气泡。
- 日常陪伴回复和沉浸模式的显式 `<messages>` 回复都不进入 token streaming store、tail replay、tail spacer 或 shrink-debt 管线；只有沉浸模式普通文本继续走现有流式与 tail replay。
- 片段 reveal 只更新父列表项的内部高度和父消息 patch，不改变已有列表项顺序，不生成临时 segment key 到外层 `VisibleMessageItem`。
- 用户仍在底部或 near-bottom 时，每次 reveal 复用现有 follow-latest 能力跟随最新气泡；用户已经向上阅读时保持当前可见位置，只显示现有“回到最新”入口，不强制拉回底部。
- 继续沿用 inverted `FlatList` 与 `maintainVisibleContentPosition`。新增片段、加载更早历史、搜索定位、内联编辑和 branch 跳转必须分别回归，不能为了日常陪伴改写现有 MVCP/tail replay 算法。

## 组件边界

为避免继续膨胀 `AiChatScreen.tsx`，实现应拆出可独立测试的边界：

- **模式策略**：计算当前会话模式、消息快照、重生成模式与待生效切换。
- **协议解析器**：只负责识别 `<messages>`、解析、清理和单气泡回退，不依赖 React Native。
- **片段仓储**：负责片段事务、父内容物化和恢复查询。
- **连发调度器**：只负责延迟预算、暂停、继续、停止和 generation 校验，不组装 prompt。
- **时间标签策略**：从升序可见消息组派生标签，不在气泡组件内临时比较日期。
- **模式 UI**：输入区模式按钮、选择面板和一次性提示。

`AiChatScreen` 负责组合这些能力与现有 generation manager，不在页面中同时承担 XML 解析、数据库事务和计时策略。

## 错误处理

- provider 失败：沿用当前可读错误与重试入口，不展示原始协议缓冲。
- 网络切换或短暂断网不会自动另起第二个 provider 请求：当前请求若能继续则沿用同一 `generationId`，若底层请求失败则按现有 network 错误进入失败终态；用户显式重试时才创建新的 `generationId`。
- provider 超时沿用现有 timeout 分类：首条显示前超时进入 `failed_before_visible`；若已有 revealed 片段，则保留已显示内容、丢弃 queued 并进入 `failed_after_partial`。超时、网络失败和用户停止不得互相伪装。
- 协议损坏：有可读正文则单气泡回退；无正文则空响应失败。
- 片段落库失败：不得先显示后假装成功；当前片段保持未显示并进入失败状态。
- 父内容物化失败：与片段状态更新同事务回滚，避免 UI、搜索和记忆看到不同文本。
- 用户打断与停止：已显示内容不删除，未显示内容永久丢弃。
- 晚到回调：静默丢弃，不弹“生成失败”。
- 页面卸载：取消 UI 计时器，但不擅自删除由 generation manager 管理的请求。
- 空会话切换模式：允许，不要求先创建消息；首次发送时模式写入消息快照。
- 删除/归档会话：片段随父消息级联处理，遵循现有会话数据规则。

## 无障碍与体验约束

- 模式按钮和三点按钮提供准确的 accessibility label、role、state 和足够触控区。
- `对方正在输入…` 使用 polite live region，避免每次队列间隔重复朗读。
- 每个新显示气泡只播报一次；后台完成后回前台不连续重复朗读全部历史。
- 字体缩放后标题、模式按钮和三点不得重叠；标题保留单行截断。
- `#EDEDED` 上的文字、图标、气泡边界需满足现有对比度标准。
- 关闭动画或系统减少动态效果时，仍保留轻微消息间隔，但不增加额外位移动画。

## 测试与验收

### 单元测试

- 正常一条、多条、空白、实体字符、空 `<msg>`、前后空白。
- emoji/组合字符、链接、引用、Markdown 表格、带 `<`/`&` 的代码块保持原子完整；损坏协议回退时正文不丢失。
- 缺根标签、未闭合、错误嵌套、协议文字泄漏和空响应回退。
- 超过 20 条时保持顺序并合并到第 20 条。
- 沉浸模式普通文本快速判定后继续现有流式输出。
- 日常陪伴完整缓冲后才产生可见片段。
- 800ms 静默窗口、2.4 秒上限、附件强制封组。
- 组内用户消息从 provider history 排除，只在 current turn 出现一次。
- 快 provider 的首条随机区间、慢 provider 不追加首条等待、条间随机区间、6 秒总预算与可注入随机源。
- 5 分钟边界、跨天、一周边界、分页边界、AI 多片段只显示一次时间。

### 状态与并发测试

- 空闲切换、生成中切换、切换后立即发送、切回沉浸模式、连续快速切换后最后一次选择落库。
- 连续消息收集期间切换模式会先封组，当前组仍使用开始收集时的 mode 快照。
- 用户在 provider 生成中插话、首条等待时插话、第二条后插话。
- 停止前无可见片段、停止后已有部分片段。
- 失败前无可见片段、失败后已有部分片段。
- provider 超时、网络失败、网络切换后晚到回调和显式重试新 generation。
- 旧 `generationId` 晚到 patch、晚到终态、晚到队列定时器全部被丢弃。
- 路由离开再返回、App 前后台切换、后台完成、进程死亡后 orphan 恢复。
- 已显示内容进入下一轮上下文；queued/discarded 内容不进入 prompt、搜索、摘要和记忆。
- Personal space 与 normal space 的恢复查询和片段数据互不串联。
- 外层列表始终保持一个父回合一个稳定 item；分段回复不触发 streaming tail item/spacer/debt，底部跟随和向上阅读位置分别保持正确。

### 数据迁移测试

- 既有会话与消息升级后均为 `immersive`，历史 UI 不变。
- 新会话默认 `immersive`，可在首条消息前切换。
- 消息版本切换后保留原 mode 与分段边界。
- 备份/恢复包含新字段和片段表；旧备份导入时有安全默认值。
- 部分显示回合的父 `content` 只包含 revealed 文本。

### Android 人工验收

1. 使用真实长历史会话升级，确认顶部精简、历史样式和普通流式回复无回归。
2. 在空会话首次看到一次性提示，选择日常陪伴后发送普通问候、情绪表达和激动连发场景。
3. 确认页面画布及顶部为 `#EDEDED`，输入区保持独立表面，无微信绿色复制。
4. 确认日常陪伴生成时标题变成静态`对方正在输入…`，无三点动画，最后一条出现后恢复名称。
5. 确认 AI 可自然回复一条或多条，气泡整条出现，不逐字显示，不机械固定条数。
6. 快速发送三至四条用户消息，确认全部立即显示，AI 能结合整组语义回答且只启动一个回合。
7. 在 AI 连发中插话，确认已显示气泡保留、未显示内容永不补发，新回复不串入旧 generation。
8. 切换模式后继续聊天，再切回；历史气泡保持生成时样式。
9. 在生成、首条等待和条间等待阶段分别切后台/返回，确认无重复、无长时间卡住、无标题残留。
10. 验证三点直接打开会话设置，`查找聊天记录` 位于会话名称之后，并可定位结果。
11. 验证 5 分钟、跨天和历史分页时间标签，不在多气泡回合中重复显示。
12. 使用大字体、慢设备和 200 条以上真实历史检查顶部不重叠、列表不跳动、输入区可用。
13. 在日常陪伴模式明确索要完整攻略、Markdown 表格和含链接/代码块的长答案，确认不自动切模式、不拆坏原子内容，回答后仍处于日常陪伴。
14. 快速往返切换模式三次并立即发送，确认按钮、数据库和生成快照均以最后选择为准，旧写入不回滚 UI。
15. 分别在底部和向上阅读时让 AI 连发多条，确认底部自然跟随、向上阅读不被强拉；再加载更早消息并使用搜索定位，MVCP 与 tail replay 无回归。
16. 在 provider 生成和片段连发阶段分别模拟断网/超时，确认无重复请求、无协议泄漏、已显示内容保留且重试创建新 generation。

## 交付约束

- 实现该用户可见能力时，同步更新 `docs/feature-matrix.md`、用户手册和内置手册对应章节。
- 新 UI 必须使用 `src/design/tokens/` 中的共享颜色、字体、间距、节奏、圆角和触控尺寸 token。
- 不改侧边抽屉，不借本需求做无关页面重构。
- 不用协议片段替换现有父消息的分支、收藏、引用或版本语义。
- 不在第一版加入 AI 主动消息，即使 prompt 或 provider 已具备相关能力。
