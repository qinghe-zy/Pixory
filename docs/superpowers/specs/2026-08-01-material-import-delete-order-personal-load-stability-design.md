# Pixory 素材导入、删除与隐私模式加载稳定化设计

## 目标

在不改变 Pixory 现有 Android-first、本地优先、原图安全和隐私空间隔离原则的前提下，补齐三类问题：

- 相册素材“删除原文件”应走 Android 系统确认链路，并在无法删除时给出明确的部分成功结果；
- 导入后的展示顺序应尊重素材来源顺序，而不是默认按导入时间；
- 隐私模式刚进入时的首页与整理页应避免一次性加载过多数据，降低卡顿和闪退风险。

## 当前现状

现有代码已经具备这些基础：

- 图片/视频导入会复制原文件到应用私有存储；
- 相册来源与文件来源已经分流；
- 资源包导入会先解压再遍历文件；
- 默认列表排序主要依赖 `createdAt` / `updatedAt`；
- 隐私模式使用独立空间，但首页和整理页仍会一次性拉取较多数据。

当前暴露的问题是：

- 删除链路只拿 `assetId` 直接调用媒体库删除，没有把“这是系统媒体资产”与“这是临时文件/包内文件”分开建模；
- 导入链路没有保留“来源时间 / 来源顺序”作为主排序依据；
- 隐私模式首屏把列表、分组、标签、统计和大量缩略图同时推进，素材一多就容易压住 Android。

## 非目标

- 不改聊天模型、memory、branch、provider 或 AI gateway 逻辑；
- 不做云相册、同步相册或远端媒体索引；
- 不把文件来源伪装成系统相册来源；
- 不压缩、覆盖、重编码或替换原图；
- 不在这个 spec 里重做整套图库 UI。

## 一、Android 删除确认

### 设计原则

删除原文件必须区分三类来源：

1. 系统相册/MediaStore 资产；
2. 文件选择器或资源包里的临时文件；
3. Pixory 自己复制到私有存储后的副本。

只有第 1 类才可能触发 Android 系统删除确认。第 2、3 类不应尝试调用系统媒体删除流程。

### 行为要求

- 对相册导入的素材，若保留了可删除的系统媒体引用，则在复制与入库成功后，再发起系统删除请求；
- 用户取消删除确认时，导入结果仍应保留，原文件继续存在；
- 若根本没有可删除的系统媒体引用，则直接标记为“原文件未删除”，不要把整批导入判失败；
- 文件来源、压缩包来源、Pixory 私有存储副本都必须强制复制，不进入删除确认流程；
- 删除前不得依赖缓存 URI 或解压后的临时文件路径反推原始媒体；
- 删除结果要可见、可统计、可回放。

### 建议实现

- 为单个素材补充稳定的来源字段，至少包含：
  - `sourceKind`：`album` / `files` / `package`
  - `sourceAssetId`：系统媒体资产 ID，只有相册来源才可能存在
  - `sourceUri`：仅用于复制、验证和日志，不作为删除依据
- 删除逻辑改成显式的“系统媒体删除请求”适配层；
- 如果系统或权限状态不允许删除，返回部分成功，而不是抛出整批失败。

### 验收

- 相册素材删除会出现 Android 系统确认；
- 取消确认后，导入成功但原文件保留；
- 文件来源和压缩包来源不会误触发删除；
- 没有可删除引用时，界面会明确提示“原文件未删除”。

## 二、导入顺序

### 设计原则

导入列表应尊重“素材来源的真实顺序”，而不是“谁先写库谁排前面”。

### 相册来源

相册导入需要保留来源时间作为主要排序键，优先级建议如下：

1. 系统媒体时间戳；
2. EXIF 拍摄时间；
3. 文件修改时间；
4. 导入时间作为最后兜底。

页面上应允许按来源时间正序或倒序查看，默认导入结果应优先显示来源顺序，而不是入库顺序。

### 压缩包来源

压缩包导入必须严格保留 zip / pixorypack 内的条目顺序：

- 不能依赖解压后目录遍历顺序；
- 不能依赖文件系统自然排序；
- 不能被入库顺序重排。

建议在扫描压缩包时显式记录：

- `sourceSequence`：压缩包内 entry 顺序，从 0 或 1 开始递增；
- `sourceEntryPath`：原始相对路径，用于调试和回放；
- `sourceKind = 'package'`。

### 混合批次

如果同一批导入里同时包含相册和压缩包来源，则：

- 相册素材按来源时间排序；
- 压缩包素材按包内顺序排序；
- 不允许用统一的导入时间把两者糊成一条序列。

### 数据模型建议

建议在 `image_assets` 上增加来源排序字段，至少包含：

- `sourceCapturedAt`：可空文本时间戳；
- `sourceSequence`：可空整数；
- `sourceKind`：来源类型；
- `sourceEntryPath`：压缩包时保留原始相对路径。

列表查询需要支持新的排序方式：

- 来源时间正序；
- 来源时间倒序；
- 包内顺序正序；
- 包内顺序倒序。

### 验收

- 相册批量导入结果顺序和相册时间一致；
- 压缩包导入结果顺序和压缩包内部顺序一致；
- 导入批次详情页不再只按入库时间排序；
- 混合来源批次不会被导入时间打乱。

## 三、隐私模式首屏性能

### 设计原则

隐私模式进入后，首页与整理页应优先“快速可见、渐进补全”，不要一口气把所有本地资产和统计都拉出来。

### 当前根因

首页和整理页的当前风险主要来自：

- 首屏一次性查询太多表；
- 列表对象太大；
- 缩略图和详情同时进入渲染；
- `useScreenLoad` 只有最终挂载保护，没有真正的请求取消；
- 隐私空间下图像缓存更保守，任何大列表都会更容易顶到内存边界。

### 行为要求

- 隐私模式首页先渲染壳和关键入口，再分阶段加载列表和统计；
- 整理页只加载当前队列的最小必要数据，详情在可见时再补；
- 大列表要分页或分段查询，不允许无上限一次性灌满；
- 快速切换隐私模式 / 返回首页 / 打开整理时，旧请求要能失效；
- 图片缩略图与列表数据分开加载，不让首屏卡在图片解码上。

### 建议实现

- 首页拆成两层：
  - 第一层只取 IP 概览、待整理计数和首屏可见列表；
  - 第二层在首屏稳定后补全额外统计与低优先级项。
- 整理页改成“当前条目 + 轻量队列 + 按需详情”；
- 对图片列表引入明确的分页边界或首屏上限；
- 为隐私空间加载增加 stale request 保护，避免重复切页时旧请求覆盖新请求；
- 保留现有 `SecureImage` 的缓存保守策略，不在个人空间里放宽缓存。

### 验收

- 刚进入隐私模式时，首页能先出现，不被全量数据阻塞；
- 打开整理页时不会因素材过多而明显卡死或闪退；
- 快速切换页面不会让旧请求回写新页面；
- 大素材库下仍能稳定进入首页和整理页。

## 四、IP 间批量流动

### 设计原则

“移动到 IP”应该表示把已选素材批量迁移到另一个现有 IP，而不是只给视频准备的特例入口。

### 行为要求

- 在全部素材、分组素材、以及其他单 IP 批量整理视图中，只要当前选择里存在可迁移素材，就应允许选择目标 IP；
- 迁移目标必须是另一个已存在的 IP，不能迁回自己；
- 图片和视频都应支持批量迁移；
- 目标 IP 在同一 space 内选择，普通空间与隐私空间保持隔离，不做跨空间迁移；
- 迁移后素材应在目标 IP 下保持可用，并保留标签、分组、收藏等可迁移元数据；
- 原始文件和缩略图应按现有“复制再清理”的安全流程处理，不允许直接改写原位置；
- 当选择跨多个来源 IP 的混合素材时，若当前 UI 视图本来就允许这种选择，也应提供统一迁移动作，但必须显式提示源 IP 混合与目标 IP 结果。

### 建议实现

- 将现有仅视频可用的“移动到 IP”入口升级为统一的素材迁移入口；
- 复用现有视频迁移的“复制到目标 IP + 软删除源素材”模式；
- 图片迁移需要和视频迁移一样：
  - 复制原图到目标 IP 私有目录；
  - 复制缩略图或重建预览；
  - 迁移标签和分组；
  - 清理源素材记录，但保留可恢复边界；
- 若目标 IP 下已存在同名分组，沿用已有分组；不存在则按当前分组规则创建或跳过；
- 迁移失败时，应能报告已迁移数量与失败原因，不应整批静默失败。

### UI 要求

- 当前没有可迁移目标时，按钮可以禁用，但禁用文案应说明是“没有可选目标 IP”而不是能力不存在；
- 若当前选择里没有可迁移素材，按钮才真正禁用；
- 批量面板里图片、视频混选时，动作说明应直接写成“移动到 IP”。

### 验收

- 全部素材页和分组素材页中，选中图片后也能批量移动到其他 IP；
- 视频仍保持现有迁移语义；
- 迁移前后，素材在目标 IP 下可继续进入浏览、整理和搜索；
- 按钮不再因为“当前是图片”而长期灰掉。

## 五、测试与验证

### 需要补的测试

- 相册来源素材在删除前保留系统媒体 ID；
- 文件来源和压缩包来源永远不会走删除确认；
- 删除取消后返回部分成功结果；
- 相册来源排序按来源时间而不是导入时间；
- 压缩包来源排序按 entry 顺序而不是文件系统遍历顺序；
- 隐私模式首页与整理页的首屏加载不会一次性拉取全量数据。
- 图片和视频批量迁移到 IP 时都能进入目标选择流程；
- 目标 IP 不能为空且不能等于源 IP；
- 迁移结果保留可见的成功/失败计数。

### 手动验证

- Android 真机上确认删除弹窗是否出现；
- 大量相册素材批量导入后，导入结果顺序是否稳定；
- 压缩包导入后，展示顺序是否和压缩包内一致；
- 刚进入隐私模式时，首页与整理页是否明显更快、更稳。

### 统一验证命令

```powershell
pnpm.cmd typecheck
pnpm.cmd test
git diff --check
```

## 备注

这个 spec 只定义产品与技术契约，不直接实现代码。正式实现前，需要按这个 spec 先补失败测试，再做最小修改，并同步更新 `docs/feature-matrix.md`。
