# Pixory 用户身份与发号系统 (UID) 架构设计

> 本文档用于记录 UID 发号系统的核心架构、部署位置及拓展指南，为未来的 A/B 测试、灰度发布、靓号派发等提供参考。

## 1. 核心架构设计

为了保证极致的本地优先体验、支持弱网环境，并杜绝重复请求对服务器造成的并发压力，Pixory 采用了 **“服务器仅分发绝对自增整数，客户端承担持久化与渲染逻辑”** 的去中心化架构。

## 2. 服务器端 (发号器)

服务器提供一个极其轻量的纯 Node.js 服务，它唯一的职责就是累加本地的计数器，并返回格式化后的字符串以及**原生整数 (raw)**。

- **服务器 IP**: 20.78.128.220 (mist01.com)
- **代码路径**: /home/qinghe/pixory-api/server.js
- **数据持久化**: 同目录下的 counter.txt 保存了绝对自增的原始计数值，该数字即为“当前总发号量”。
- **进程管理**: 由全局安装的 pm2 后台守护，进程名为 pixory-id，已配置开机自启。
- **网关代理**: 在 /etc/nginx/sites-available/mist01.com 中配置了反向代理，将公网 https://mist01.com/api/get_id 代理至本地的 http://127.0.0.1:3001。

## 3. 客户端 (App端)

客户端在 App.tsx 的全局入口启动时，会静默无感地发起网络请求，并在拿到号码后进行永久级别的双重本地固化。

- **核心服务**: src/services/uidService.ts。取号、网络 3 秒熔断、并发锁、重试逻辑等均封装于此文件。
- **双重本地缓存**: 使用 SecureStore (随 App 卸载或清空数据而销毁)，且一旦存在本地数据，终生不再发起网络请求。
  - pixory.uid.current: 保存服务器返回的格式化字符串 (如 AAA-001)。当前界面 (MeScreen) 的展示直接读取此键。
  - pixory.uid.raw: 保存服务器同步下发的原生整数序号 (如 1)。该数字是后续前端扩展的基石。

## 4. 后期拓展指南

### 4.1. 前端去中心化 A/B 测试与灰度发布
后期如果需要进行 A/B 测试或灰度发布，**无需任何服务器交互**。
请直接读取本地的 pixory.uid.raw，将其转换为整数后进行取模运算。例如：
`	ypescript
const rawId = parseInt(await SecureStore.getItemAsync('pixory.uid.raw'));
if (rawId % 2 === 0) {
  // A 组实验策略
}
`
由于 aw 在客户端永久固化，这种分组方式具有**绝对确定性**和**跨版本持久性**。

### 4.2. 强制全员重置账号体系
如果未来业务大改，需要强推新账号体系（废弃当前的 AAA 格式），**无需修改服务端**。
只需在客户端修改 src/services/uidService.ts 中的 UID_KEY 常量（例如改为 pixory.uid.v2）。全量用户更新 App 后，由于查询新 Key 为空，会自动集体向服务器申请新号。

### 4.3. 靓号锁仓与定向人工派发
- **锁仓**：若需保留早期号段（如雪藏前 10 号），只需直接登录服务器，将 counter.txt 的内容改为 10 即可。下一个自然注册的用户将从 11 开始获取。
- **定向派发**：后续若要将保留的“靓号”送人，由于发号系统**认本地不认服务端**，只需在 App 前端编写一个隐藏入口（如点击 5 下关于页的 Logo 弹出兑换码输入框）。输入暗号后，通过代码强制覆写该用户手机里 SecureStore 的 pixory.uid.current 和 pixory.uid.raw，重启 App 即永久生效。
